Финальный проект курса. Репозиторий команды: https://github.com/MaksChocomint/llm-project
Команда: Иванов Максим Сергеевич (ИСУ 564789), Клементьев Кирилл Алексеевич (ИСУ 564092), Семенов Константин Владимирович (ИСУ 439369)
Модель: qwen3:4b-instruct-2507-q4_K_M, эмбеддинги bge-m3, Ollama 0.40 на NVIDIA RTX 2060 SUPER, temperature 0, seed генерации 7. Для алгоритма Лувена seed 42

1. Задача

Диспетчер «ПолярТех» принимает звонок: «витрина AR-210, на панели E-17». Чтобы отправить инженера с нужной деталью, ему надо пройти цепочку из нескольких документов. В руководстве к модели код ошибки указывает на отказавший узел, а в разделе «Состав узлов» узлу соответствует номер детали. Сервисный бюллетень может сообщить, что эта деталь снята с производства и заменена другой, иногда через две замены подряд. Остаток на складе и цена хранятся уже не в документах, а в учётной системе (ERP). Оформить заказ можно только после того, как его подтвердит человек. Отдельный класс вопросов обзорный: «какой узел чаще всего отказывает в линейке», и ответ на него собирается из десятков отчётов о выездах.

Плоский RAG ищет несколько похожих на вопрос фрагментов текста и отвечает по ним. Пример ошибки из нашего прогона:

dev-06 (multihop): «Какую деталь заказать при ошибке E-17 на AR-210?» Верный ответ: P-1042B.

baseline: При ошибке E-17 на AR-210 отказ узла «пусковое реле», поэтому необходимо заказать деталь «пусковое реле». … Ответ: пусковое реле.

Причина. Плоский RAG нашёл руководства AR-210, AR-310, AR-220 и BZ-210: во всех есть одинаковый список кодов ошибок, поэтому все они одинаково похожи на вопрос. Номер детали P-1042 из раздела «Состав узлов» AR-210 до модели либо не дошёл, либо не был связан с узлом, а бюллетень SB-2025-03 о замене P-1042 на P-1042B в найденные фрагменты не попал совсем: по смыслу он на вопрос не похож. Ответ требует трёх переходов (E-17 → пусковое реле → P-1042 в AR-210 → P-1042B), а близость по эмбеддингам находит только первый. На обзорных вопросах (dev-13…dev-16) плоский RAG отвечает «не найдено» во всех четырёх случаях: подсчёт по 40 отчётам не помещается в несколько фрагментов.

2. Решение

Конвейер: документы → чанки (92) → извлечение моделью → граф (118 узлов, 276 рёбер) → сообщества Лувена (8) со сводками. Поверх графа работают два режима поиска и агент с пятью инструментами.

Извлечение (extraction.py, FR-1)

  • Запрос содержит типы сущностей, все 8 типов связей с направлением («HAS_PART: Model → Part…»), закрытый словарь названий и один пример. Ответ задаётся JSON-схемой EXTRACTION_SCHEMA.
  • Наше решение: отдельное правило «для каждой строки состава узлов выдай три связи: HAS_PART, IS_A, SUPPLIED_BY». Без него модель у 6 из 12 руководств выдавала HAS_PART только для одной детали из восьми (раздел 5, ошибка 1).
  • Проверка по тексту. Код принимается, только если он есть в тексте чанка. Название должно быть из словаря. Наше решение: линейка и поставщик тоже должны быть названы в чанке. Без этого модель приписывала моделям линейку из примера в запросе (раздел 5, ошибка 2).
  • Устойчивость. Если JSON неполон или структура ответа нарушена, модель получает один повторный запрос с пояснением. После второй неудачи чанк возвращает пустой результат. Счётчик dropped учитывает сущности и связи, отброшенные при проверке разобранного ответа.

Граф (graph_builder.py, FR-2)

  • Узел имеет вид Тип:Имя. Вес ребра равен числу разных чанков, где найдена связь, поэтому повторы внутри одного чанка вес не завышают. У каждого ребра хранятся источники.
  • Если между двумя деталями есть REPLACED_BY в обе стороны, остаётся связь с большим весом, а при равенстве удаляются обе. На полном корпусе таких конфликтов 0.

Сообщества и сводки (communities.py, FR-3)

  • Алгоритм Лувена с seed=42 на неориентированной версии графа с весами.
  • Все числа считает код по весам рёбер: отказы узлов и моделей по каждой линейке, детали из руководств линейки, снятые с производства, цепочки замен, отказы по моделям и узлам, число деталей у поставщика.
  • Сводку пишет модель одним вызовом по готовым подсчётам, ответ обрезается до 150 слов. В промпте два требования: писать только о том, что есть в подсчётах, и переносить каждое число вместе с линейкой, моделью или узлом, к которым оно относится. Оба появились после ошибок прогонов (раздел 5, ошибка 3).

Поиск по графу (search.py, FR-4, FR-5)

  • local. Опорные узлы ищутся кодом без модели (find_codes, find_names). Если в вопросе есть код, которого нет в графе, поиск отказывает без вызова модели. При двух и более опорных узлах берутся все простые пути длиной до 3 связей без учёта направления, при одном берётся окрестность глубиной 2. К фактам добавляются цепочки замен и поставщики деталей на путях. Факты упорядочены по важности и обрезаются до 8000 символов. Модель отвечает только по пронумерованным фактам. Коды в ответе, которых нет в фактах, отправляются модели на одно исправление, затем ответ заменяется отказом.
  • global. Работает в два шага. На шаге map каждая сводка получает частичный ответ и оценку полезности 0–10 (MAP_SCHEMA). Все частичные ответы с оценкой выше 0 объединяются на шаге reduce одним вызовом модели. Если таких нет, поиск отказывает. В запросе reduce вопрос стоит перед частичными ответами (раздел 5, ошибка 8). Неизвестный код в вопросе означает отказ, как и в local (FR-10).

Агент (agent.py, tools.py, validation.py, FR-6…FR-10)

  • Пять инструментов: search_knowledge (local), summarize_topic (global), check_stock, get_price, create_service_order. Поиск по графу для агента такой же инструмент, как запросы в ERP.
  • Проверки до вызова инструмента:
    • номер детали должен уже встречаться в вопросе или в результатах инструментов;
    • количество в заказе должно быть названо пользователем;
    • склад и модель должны быть допустимыми;
    • деталь, снятая с производства, не заказывается;
    • повторный вызов с теми же аргументами берёт прежний результат.
  • Ограничения: при недоступности ERP делается 3 попытки, всего агенту доступно не больше 6 вызовов инструментов.
  • Перед выдачей ответа коды, цены и остатки сверяются с вопросом и результатами инструментов, включая искажённые коды вида SP-1044. Даётся одна попытка исправления, при повторном расхождении агент отказывает.
  • Наши решения:
    • если модель отвечает, не вызвав ни одного инструмента, её один раз просят сначала свериться с базой знаний;
    • если пользователь просил оформить заказ, а create_service_order не вызван, модель возвращают к заказу;
    • summarize_topic при отказе пробует точный поиск, на случай если модель выбрала не тот инструмент.

4. Где граф помогает и где уступает

Помогает: многошаговый вопрос dev-06 и обзорный вопрос dev-13

dev-06: «Какую деталь заказать при ошибке E-17 на AR-210?» Baseline ответил узлом вместо детали (раздел 1). Ответ local:

1. Ошибка E-17 указывает на отказ пускового реле (факт 5). 2. Пусковое реле является деталью AR-210 (факт 6). … 4. Деталь P-1042 (пусковое реле) заменена на P-1042B (факт 1). … Ответ: Заказывать деталь P-1042B, поставщика ХолодКомплект.

Опорные узлы E-17 и AR-210 найдены кодом. Путь E-17 → пусковое реле ← P-1042 ← AR-210 лежит в пределах трёх связей, а цепочку замен P-1042 → P-1042B добавляет код. В контекст модели попали все четыре нужных факта из трёх разных документов, и ей осталось только их пересказать. На вопросах multihop local даёт 1.00 против 0.57 у baseline, при этом в среднем токенов на вопрос меньше (1153 против 1358).

dev-13: «Какой узел чаще всего отказывает в линейке «Арктика»?» Baseline: «в базе знаний не найдено». Global: «Пусковое реле».

Ответ взят из сводки сообщества: «Фрагмент включает линейку «Арктика» с моделями AR-210, AR-220, AR-310, AR-320. В ней встречаются отказы узлов: пусковое реле (9), датчик температуры (4), контроллер (1)». Это число собрано кодом по рёбрам FAILED из десятков отчётов, а плоский RAG видит только 4 фрагмента.

Уступает: global на точных вопросах и зависимость от качества извлечения

dev-07, режим global: «Какую деталь заказать при ошибке E-22 на GS-510?» Верно: P-3162. Ответ global: «необходимо заказать деталь P-3062C».

Сводки строятся по сообществам, а Лувен группирует узлы по поставщикам и узлам, не по моделям. В сводке о циркуляционных насосах есть цепочка замен P-3062 → P-3062B → P-3062C (насос других моделей), но нет связи «GS-510 содержит P-3162». Модель взяла единственный подходящий код из сводки и ошиблась. На вопросах multihop global даёт 0.14 против 0.57 у baseline и при этом заметно дороже: 7.5 вызова и 3244 токена на вопрос против 1 вызова и 1358 токенов.

dev-01 в прогоне 1, режим local: «По какому регламенту устраняют ошибку E-17?» Baseline: «По регламенту SP-104» (верно). Local: «в базе знаний не найдено».

Модель при извлечении пропустила связь E-17 → SP-104 из регламента. Плоский RAG прочитал регламент напрямую, а граф знает только то, что извлекла модель, поэтому local отказал. После того как в промпт добавили правило о фразе «Регламент SP-… применяется при ошибке E-…», связь появилась. В прогонах 2 и 3 local дал верный ответ. В итоговом прогоне связь присутствует, но local вернул отказ после проверки сгенерированного кода (ошибка 4).

5. Ошибки

№ Этап Ошибка и пример Причина и что сделано
1 Извлечение В прогоне 1 у AR-210, AR-220, BZ-120, GS-410, GS-510 и GS-520 в графе по одной связи HAS_PART вместо восьми. Local и агент не находили деталь модели: dev-06, dev-07, dev-08, dev-17, dev-18, dev-21. Модель выдавала IS_A и SUPPLIED_BY для каждой детали, а HAS_PART только для одной. Добавили правило «три связи на каждую строку состава узлов». Recall связей вырос с 0.88 до 0.99, multihop в local вырос с 0.43 до 1.00.
2 Извлечение Ложные связи BELONGS_TO: BZ-210 → «Гольфстрим» (из отчёта R-2025-017, где линейка не названа), GS-410, GS-420, GS-510, GS-520 → «Арктика» (из второй части руководств, где линейки нет). В прогоне 2 local ответил на dev-04 «BZ-210 входит в линейку Гольфстрим». Модель угадывала линейку, во втором случае копируя её из примера в запросе. Линейки и поставщики теперь проверяются по тексту чанка, как коды. Precision связей вырос с 0.98 до 1.00, а 39 таких сущностей на корпусе отброшены.
3 Генерация (сводки) Global на dev-13 ответил «Реле давления (код E-16)» вместо «пусковое реле». В прогоне 1 на обзорных вопросах 0 верных из 4. Модель получала голые числа без привязки и при пересказе перемешала их. Теперь код пишет каждое число в готовой фразе с названием линейки («Отказы узлов в линейке «Арктика» по отчётам: пусковое реле – 9, …»), а промпт требует переносить числа вместе с ней. Вторая ошибка той же природы: пока промпт перечислял, о чём писать («линейки, модели, отказы по линейкам»), модель для сообществ без линеек выдумывала «линейку 123» и «модель 456». Теперь промпт разрешает писать только о том, что есть в подсчётах. Результат на обзорных вопросах: 4 из 4.
4 Генерация и проверка Агент на dev-01 ответил «По регламенту SP-1044», и проверка выдуманных фактов этот код не поймала. На dev-01 при генерации ответа local возник код «SP-1042»: модель склеила SP-104 с соседним в фактах кодом P-1042. Функция find_codes пропускает строки неверного вида, поэтому SP-1044 не считался кодом вообще. Добавили malformed_codes, и такие ответы уходят модели на одно исправление. Агент теперь отвечает верно. В local модель после исправления пишет «не найдено». Это ошибка (local 0.80 на вопросах local), но безопасная: вместо неверного регламента система отказывает.
5 Инструмент и генерация В прогоне 2 агент на dev-21 («Оформи заказ: 2 штуки…») вызвал check_stock и get_price, не вызвал create_service_order и написал «Заказ оформлен на 2 штуки». Реального заказа не было: без вызова инструмента создать его невозможно. Но текст ответа ложный. Теперь агент возвращает модель к create_service_order, и заказ доходит до подтверждения человеком (раздел 6).
6 Генерация и вывод цены На dev-19 модель приводила лишь цену «17210 руб.». Пользователь указал название узла и модель оборудования, но из ответа не мог узнать номер найденной детали. Если ответ целиком состоит из цены, а в вопросе нет артикула, агент добавляет номер из успешного запроса цены при однозначном совпадении. Итоговый ответ: «P-2022: 17210 руб.». Дополнительного вызова модели не требуется.
7 Поиск (воспроизводимость) При проверке на чистом запуске в Docker local и agent не воспроизводились из кеша: модель недоступна, а запросы в кеше не находились. Соседей узла мы брали через graph.to_undirected(as_view=True), а networkx объединяет их через множество, и порядок зависит от PYTHONHASHSEED. Поэтому порядок фактов, а значит и ключ кеша, менялся от запуска к запуску. Теперь неориентированная копия графа строится с сортировкой узлов и рёбер, и повторный прогон даёт идентичные ответы.
8 Генерация (reduce) Агент на dev-16 вызвал summarize_topic с вопросом «какие детали из линейки «Бриз» сняты с производства». На шаге map сводка «Бриз» дала частичный ответ «Детали P-2054, P-2110 сняты с производства» с оценкой 10, и это был единственный ответ с оценкой выше 0. Reduce всё равно ответил «в базе знаний не найдено». В частичном ответе нет слова «Бриз», и модель, прочитав вопрос после ответов, сочла их не относящимися к делу. Промпт reduce теперь объясняет, что частичные ответы получены из сводок по теме вопроса, а вопрос стоит перед ними. В итоговом прогоне агент верно ответил на dev-16, а global решил все четыре обзорных вопроса.

Доля ответов с выдуманными фактами: агент 0.000, baseline 0.000, global 0.000, local 0.042. В local это единственный ответ, на dev-21: метрика пометила как выдуманный остаток «2 шт», хотя это количество из вопроса («2 штуки детали»). Local к ERP не обращается и заказ не оформляет, поэтому ответ всё равно неверный. Но выдуманной цены или остатка в нём нет.

6. Границы системы

Единственное действие с последствиями — создание заказа в ERP (create_service_order). Оно никогда не выполняется без подтверждения человека, и обеспечено это кодом, а не просьбой в промпте:

  • Без флага confirm=True (в CLI это ask --confirm, в HTTP API поле confirm) агент может читать цены и остатки ERP. Перед созданием заказа он останавливается и возвращает needs_confirmation=True и pending_action с готовыми аргументами заказа. Пример из итогового прогона, dev-21:
    Подготовлен заказ: деталь P-2054C, 2 шт., склад Москва, модель BZ-120. Заказ будет создан после подтверждения. pending_action = {"tool": "create_service_order", "args": {"part_id": "P-2054C", "warehouse": "Москва", "qty": 2, "model": "BZ-120"}}
  • Даже при confirm=True заказ отклоняется, если количество не названо пользователем: агент задаёт уточняющий вопрос, а не подставляет число сам. Заказ отклоняется и в том случае, если номер детали не встречался в вопросе или ответах инструментов, или если деталь снята с производства.
  • Числовую цену агент сверяет с полем price_rub успешного вызова get_price, остаток — с qty вызова check_stock. Регрессионные тесты проверяют подмену цены цифрами из артикула и подмену заказанного количества суммой бюджета. При недоступности ERP делается 3 попытки, после чего агент прямо сообщает «Данные ERP получить не удалось» и ничего не придумывает.
  • Все контрактные тесты агента (tests/contract/test_tools_and_agent.py) проходят, в том числе тесты на ожидание подтверждения и на заказ без названного количества.

7. Следующий шаг

Проверка полноты извлечения кодом с точечным перезапросом. В разделе «Состав узлов» число строк вида «узел – деталь P-…» известно заранее. Если связей HAS_PART для модели меньше, чем таких строк, модель запрашивается повторно только по недостающим строкам. Сейчас полнота держится на формулировке промпта, и ошибка 1 показала, насколько это хрупко: тот же шаблон давал 8 связей у одних моделей и 1 у других.

Как проверить. Нужно прогнать make eval-extraction и make eval MODE=local на второй модели, без правки промпта (например, gemma4:e4b, она уже есть в Ollama). Гипотеза: с проверкой полноты Recall связей останется не ниже 0.98, а multihop в local не ниже 0.86. Без неё оба числа при смене модели упадут. Дополнительная метрика — доля моделей, у которых в графе ровно 8 связей HAS_PART: сейчас 12 из 12.
